# 文档同步习惯

> 2026-10 文档瘦身后，项目只有两份核心文档。旧的 USER_GUIDE / PROJECT_QA /
> ARCHITECTURE_CN / AGENT_TOOLS 已删除（git 历史可查），不要再引用或重建它们。

## 触发时机

- 用户明确要求同步/更新文档（如"同步文档"、"更新文档"）
- 完成有意义的功能迭代后（新 API、新通路、调度层/Agent/工具变化、有架构影响的 bug 修复）
- 不适用于：纯重构、typo 修复、纯内部改动

## 两份核心文档定位

| 文件 | 侧重点 | 更新内容 |
|------|--------|----------|
| `README.md` | 英文项目概览 + 亮点 + 快速上手 | 功能亮点、关键数字（Agent 数/工具数/测试数）、架构图 |
| `docs/ARCHITECTURE.md` | **中文唯一架构基准** | 业务通路、意图→链映射、Agent/工具清单、调度语义、Backlog |

## docs/ARCHITECTURE.md 的特殊地位

它是**系统唯一权威文档**，回答：

1. **业务通路**（第 3 章）：每条通路从 API 入口到工具落地的完整调用链，新闻解读为 P0
2. **调度语义**（第 4 章）：AgentContext 数据流、context 合并规则、ScoringAgent 通用接口
3. **能力清单**（第 5-6 章）：3 Agent + 37 工具，与 registry 实际注册一致
4. **Backlog**（第 8 章）：P0/P1/P2 分级，业务通路优先、历史债降级

**更新时机**：
- 新增/修改通路、intent、Agent、工具时 → 同步第 3/5/6 章
- 修复 Backlog 中的问题时 → 从第 8 章移除或降级该条目
- 关键数字变化（工具数/测试数）→ 同步 README 与第 6/9 章

## 核心规则

1. **只更新事实性变更**：只记录实际发生的改动，不做"顺便优化"
2. **代码即真理**：文档与代码冲突时以代码为准，并立即修正文档
3. **不写未实现的功能**：功能没落地就不写文档
4. **最小编辑**：只改相关段落，不重写"可以更好"的内容
5. **Backlog 是活清单**：问题修复即删条目，不保留历史陈述

## 工作流程

1. 识别本次迭代的变更（看 attached_files 或最近 commit）
2. 检查两份文档，判断变更是否事实性相关
3. 只更新相关段落，最小化编辑
4. 通路/清单变化 → 同步 ARCHITECTURE.md 对应章节
5. 关键数字变化 → 同步 README.md

## 反模式（禁止）

- ❌ 重建已删除的 USER_GUIDE / PROJECT_QA / ARCHITECTURE_CN / AGENT_TOOLS
- ❌ 给未实现的功能写文档
- ❌ 重写"可以更好"的整段内容
- ❌ 只影响 1 个文档时更新全部 2 个
