# 文档同步习惯

## 触发时机

- 用户明确要求同步/更新文档（如"同步文档"、"更新文档"）
- 完成有意义的功能迭代后（新 API、新 UI 功能、有架构影响的 bug 修复）
- 不适用于：纯重构、typo 修复、纯内部改动

## 五大核心文档定位

| 文件 | 侧重点 | 更新内容 |
|------|--------|----------|
| `README.md` | 项目亮点 + 快速上手 | 新功能亮点、技术栈变化、Quick Start 提示 |
| `docs/ARCHITECTURE.md` | 英文模块职责 + 数据流 + 端点表 | 模块表、端点表、数据流图、新文件描述 |
| `docs/ARCHITECTURE_CN.md` | 中文系统理解指南 + 模块目标 | 用户操作路径、模块目标定义、扩展模式指南、各模块应该做成什么样 |
| `USER_GUIDE.md` | 操作指南 + 功能说明 | 用户可感知的功能变化、UI 变更、新操作流程 |
| `docs/PROJECT_QA.md` | 面试向 Q&A 记录 | 新增 Q+N 条目、关键数字表 |

## ARCHITECTURE_CN.md 的特殊地位

`ARCHITECTURE_CN.md` 不仅是文档，更是**系统的模块目标指导书**。它回答：

1. **用户操作路径**：导入/查询/分析/K线，每条路径系统怎么工作
2. **各模块应该做成什么样**：每个模块的目标、边界、质量基线
3. **扩展模式**：新增 Tool/Agent/数据源/意图/字典时怎么做（含代码示例）
4. **目录树注释**：一眼看清文件结构
5. **中文速查表**：快速定位关键概念

**更新时机**：
- 新增/修改模块时 → 更新对应模块的目标描述
- 架构调整时 → 更新数据流图和扩展模式
- 新增扩展模式时 → 追加到第 4 章

## 核心规则

1. **只更新事实性变更**：只记录实际发生的改动，不做"顺便优化"
2. **增量 Q&A**：PROJECT_QA 只追加新条目（Q+N），不重写已有条目
3. **关键数字表同步**：指标变化时（测试数、工具数、commit 数等）更新底部汇总表
4. **不写未实现的功能**：功能没落地就不写文档
5. **ARCHITECTURE_CN 模块目标同步**：模块能力变化时更新目标描述

## PROJECT_QA 条目模板

```markdown
## Q{N}: {问题描述}？

**问题**：{现象描述}

**发现方式**：{怎么发现的}

**根因**：
- {根因 1}
- {根因 2}

**修复**：
- {修复措施 1}
- {修复措施 2}

**效果**：{量化结果}

**教训**：{可复用的经验}
```

## 工作流程

1. 识别本次迭代的变更（看 attached_files 或最近 commit）
2. 逐个检查五个文档，判断变更是否事实性相关
3. 只更新相关段落，最小化编辑
4. 新功能/修复 → 追加 Q&A 条目到 PROJECT_QA.md
5. 模块能力变化 → 同步 ARCHITECTURE_CN.md 的模块目标
6. 指标变化 → 同步更新关键数字表

## 反模式（禁止）

- ❌ 重写"可以更好"的整段内容
- ❌ 给未实现的功能写文档
- ❌ 只影响 1-2 个文档时更新全部 5 个
- ❌ 修改已有 Q&A 编号（保持稳定，只追加）
- ❌ ARCHITECTURE_CN 的模块目标写成 wish list（只记录已实现的目标）
